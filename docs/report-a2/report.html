1. Application and deployment architecture

SlotHub (Assignment 1) is a multi-tenant slot-booking platform of four .NET 10 microservices. Scheduling owns slots and concurrency-safe holds. Booking orchestrates hold → pay → confirm. Payment is a mock gateway and Notification a mock SMS/email sender. Each service has its own PostgreSQL database and login. The main workflow is create booking (hold a slot), pay, confirm, notify. It exercises synchronous REST calls between services, an outbox, and idempotent retries.

2. Docker containerization (Task 1)

  • One Dockerfile per service (services/<name>/Dockerfile), multi-stage. The SDK stage restores from project files first (a cached layer) and then publishes. The runtime stage has only the ASP.NET runtime and the app (≈ 386 MB). It runs as non-root user 1654, exposes 8080, and carries OCI labels (version, git revision). Images are tagged slothub-<service>:1.0.0.
  • Health check in the image: HEALTHCHECK runs infra/docker/healthcheck.sh, an HTTP GET of /health/ready over bash's /dev/tcp (the runtime image has no curl). A container is healthy only when the service is up and its database is reachable.
  • Configuration only through environment variables: connection strings, service URLs, timeouts, hold TTL, chaos settings. Nothing environment-specific is in an image.
  • No secrets in images or the repository: .dockerignore excludes .env. Passwords come from the git-ignored .env, and docker-compose.yml uses ${VAR:?…}, so Compose refuses to start without them. .env.example holds CHANGE_ME placeholders. The database runs as a container.

Evidence (evidence/a2-task1-containerization/, 22/22 checks): docker compose build --no-cache with every build stage (raw log attached), 4 separate images with labels, containers created, started and healthy; per image, no password in env vars or history and no .env file. For the repo, .env is untracked and the examples hold placeholders only.

3. Docker Compose deployment (Task 2)

cp .env.example .env then docker compose up --build starts PostgreSQL and the four services. Start-up is health-gated: services wait for PostgreSQL to be healthy, and Booking waits for Scheduling and Payment to be healthy. It only waits for Notification to start, because notifications go through an outbox and an SMS outage must never block bookings. Restart policy unless-stopped and a named volume keep the data.

4. Situated learning: deployment troubleshooting (Task 3)

Problem. In Assignment 1, the first docker compose up failed before any service started: ports are not available: exposing port TCP 0.0.0.0:5432 … bind: address already in use. Every container stayed Created. Moving the mapping to 5433 failed the same way. The code had worked in development, where dotnet run used a PostgreSQL installed on the laptop.

Diagnosis. scripts/a2-troubleshoot-demo.sh reproduces it safely: a throw-away process holds the database's host port. Then we used:

CommandFinding
docker compose ps -aall containers Created: the failure is at container start, not inside an application
docker inspect slothub-postgres (.State, .HostConfig.PortBindings)state created; it is trying to bind container 5432 to a host port
docker compose logs postgres0 lines: PostgreSQL never ran, so the cause is outside the container
lsof -nP -iTCP:<port> -sTCP:LISTENa non-Docker process owns the port (originally the laptop's own PostgreSQL; 5433/5434 belonged to other projects)

Solution and validation. The host side of the mapping was hard-coded. It became configuration with an unused default, "${POSTGRES_PORT:-5440}:5432", set in .env. Container-to-container connections keep using postgres:5432, and no code or image changed. After the fix, all 5 containers are healthy, a booking is held, paid and confirmed, and the database answers on the new host port (12/12 checks; full workflow in Task 2 evidence).

Learning. Host ports are shared and scarce; container ports are not. Publish as few as possible, make them configurable, and never publish the database in production. "Works on my machine" hid a dependency on a locally installed database, and containerization made the environment explicit. Diagnose from the outside in (state → configuration → logs → host), where empty logs pointed away from the application. Platform details matter: on macOS, Docker publishes ports on [::], so only a dual-stack listener collides. In a real deployment we would run pre-flight port checks, keep ports in environment variables, use health-gated start-up, and in Kubernetes use ClusterIP Services so internal components need no host ports at all.

5. Advanced: Minikube deployment, scaling and self-healing (Part B)

  • Manifests (deploy/k8s/): namespace; PostgreSQL StatefulSet with a 1 Gi PVC and an init script from a ConfigMap (4 databases, 4 logins); a ConfigMap per service; 4 migration Jobs; per service a Deployment (startup and liveness probes on /health, readiness on /health/ready, requests and limits), a ClusterIP Service for in-cluster calls and a LoadBalancer Service on 5101–5104 for the host (minikube tunnel).
  • Secret slothub-db is created from .env by scripts/k8s-deploy.sh and is never committed. Pods build the connection string with $(DB_PASSWORD).
  • Migrations once, not per replica: the same image with MIGRATE_ONLY=true migrates and exits (new code path), so replicas never migrate concurrently.
  • Images are built with Docker and streamed into the node's containerd (docker save | ctr images import), with no registry.

Main workflow through Kubernetes17/17: objects healthy, Jobs completed; one booking traced through the Booking, Scheduling, Payment and Notification pods; full e2e-booking.sh 26/26 and Challenge 1 (1 of 20) through the Kubernetes Services
Scalingkubectl scale … --replicas=3 (Scheduling, Booking): 30 simultaneous holds through the load-balanced Service were spread over all 3 pods, with still exactly 1 success. With 3 hold-expiry workers, each of 5 expired holds was released exactly once (FOR UPDATE SKIP LOCKED)
Self-healingA Booking pod was deleted while 6 bookings were made: all 6 confirmed, a replacement pod was created and 3/3 were ready again. The only Payment pod was deleted, recreated, and the flow worked
ReadinessPostgreSQL scaled to 0: all service pods 0/1 and their endpoints ready=false. Back to 1: pods ready, data intact on the PVC
Why scaling is safe: no state lives in a pod. Capacity is one atomic SQL update, idempotency a database unique key, and expiry uses SKIP LOCKED, the Assignment 1 challenge mechanisms. Kubernetes problem we hit: the first deploy imported images built before the MIGRATE_ONLY change, so the migration Jobs ran a web server and never completed (kubectl get pods showed them Running, kubectl logs showed relation "holds" does not exist). The fix was to rebuild and re-import. Lesson: give each build a distinct tag.
