1. Problem and scope

SlotHub is a multi-tenant booking platform for any business that sells time, such as clinics, salons, sports turfs and tutors. A business (tenant) publishes slots for its resources (a doctor, a court). A customer holds a slot, pays, and receives an SMS/email confirmation. An unpaid hold is released automatically. The domain was chosen because it naturally contains every distributed-systems problem the brief asks for, and because one engine can later serve many industries as a product.

Assignment conditionHow SlotHub meets it
(a) ≥ 4 servicesScheduling, Booking, Payment (mock gateway), Notification (mock SMS/email): four distinct responsibilities, four databases
(b) Transaction over ≥ 3 servicesBook: Booking → Scheduling (hold) → Payment (charge) → Scheduling (confirm) → Notification (via outbox)
(c) Contended resourceSlot capacity (1 for a doctor, N for a class)
(d) Unsafe to repeatCreating a booking, paying, cancelling, charging, refunding
(e) Slow / failing dependencyMock payment gateway and SMS provider with runtime failure and latency injection (PUT /api/v1/admin/chaos)

Business rules

IDRuleOwner
BR1A slot never has more active holds (HELD + CONFIRMED) than its capacity.Scheduling
BR2A hold expires after HOLD_TTL_SECONDS (30 s in the demo) if not confirmed and its capacity is returned; a confirmed hold is never expired.Scheduling
BR3A booking is confirmed only after a successful payment and while its hold is active; a payment that completes after the hold expired is refunded automatically.Booking
BR4The same Idempotency-Key with the same payload returns the original result with no new effect; with a different payload it is rejected (422).Booking, Payment
BR5Cancellation refund: ≥ 24 h before the slot 100 %, < 24 h 50 %, after start not allowed.Booking
BR6A slot that has already started cannot be held.Scheduling

Assumptions. Fixed price per service offering, snapshotted onto the hold. Integer minor units (paise). UTC timestamps. Customers are identified by ID plus phone/email in the request. Out of scope (per brief): authentication, UI, real payment/SMS integration. Assignment 2 deployment (Minikube) is not part of this report; Dockerfiles exist only to run the stack locally.

2. Service decomposition

ServiceResponsibility (one sentence)OwnsDoes not own
Scheduling :5101Defines what a tenant offers and when, and controls how much of each slot is left.Tenants, resources, offerings, prices, slots, holds; hold expiryBookings, money
Booking :5102Takes a booking from request to confirmation or cancellation, orchestrating the others.Bookings, state machine, status history, outbox, idempotency keysCapacity, payments
Payment :5103Charges and refunds money exactly once per request (mock gateway).Payments, refunds, idempotency keys, chaos settingsWhy money moved
Notification :5104Delivers customer messages once and retries failed deliveries.Messages, delivery attempts, templates, chaos settingsBooking state

Why these boundaries. We split by business capability and by rate of change. Catalog and availability are one service (Scheduling) because a service's duration defines how its slots are cut, so they always change together. Splitting them would create a distributed monolith and add a hop to every booking. Booking is the only orchestrator: it is the one place that knows the end-to-end flow and its compensations. The other services expose small, reusable, idempotent capabilities. Payment is separate because it is the slow/failing dependency and money needs its own audit trail and idempotency. Notification is separate because its failure must never affect a booking and its channels will multiply independently.

Alternatives rejected. (1) Separate Catalog and Availability services: they change together, and one more network hop. (2) Payment inside Booking: it loses the failing-dependency boundary and the second idempotency layer. (3) A Customer service: it would be a CRUD wrapper while authentication is out of scope. (4) Choreography with events only: the flow and its compensation would be scattered across services and harder to test (see D2).

Ownership and cross-service references. Four databases on one PostgreSQL server locally, each with its own login. The init script revokes CONNECT from PUBLIC, and we verified that booking_user cannot connect to scheduling_db. There are no foreign keys across services: references (slot_id, hold_id, payment_id, booking_id) are plain UUIDs. Data a service needs at transaction time is copied as a snapshot: the hold snapshots the price and slot start, and the booking copies them. Booking can then apply BR5 without calling Scheduling, and a later price change never alters an existing booking. Enums are stored as UPPER_SNAKE_CASE text, the same as in JSON, so database rows read like API responses.

Error model. All four services return RFC 9457 Problem Details through one shared handler, including validation errors (FluentValidation), malformed JSON and unknown routes. 6. Engineering challenges

Challenge 1: Concurrency control (BR1)

Problem. Many customers try to hold the last unit of a slot at the same instant. Design. Check and increment are one SQL statement: UPDATE slots SET reserved_count = reserved_count + 1 WHERE id = @slot AND reserved_count < capacity AND start_at > now(). PostgreSQL row-locks the slot during the update, so concurrent requests queue. Each re-evaluates the WHERE against the committed value, and 0 rows affected means 409 SLOT_UNAVAILABLE. The hold insert is in the same transaction, and a CHECK constraint is a second line of defence. Why check-then-update fails: with if (slot.Reserved < slot.Capacity) { slot.Reserved++; Save(); }, every request reads 0, every request passes the check, and every request writes 1. We built that version behind CONCURRENCY_MODE=naive to show it.

Evidence (evidence/challenge-1-concurrency/)Result
20 simultaneous requests, capacity 1 (FIFO barrier releases all at once)1 × 201, 19 × 409 SLOT_UNAVAILABLE; reserved_count = 1; one HELD row
30 simultaneous requests, capacity 55 × 201, 25 × 409; reserved_count = 5
Same 20 requests against the naive instance20 holds for capacity 1, reserved_count = 1 (lost updates)
Integration test, real PostgreSQL: 20 and 50 parallel reservationsexactly capacity reserved

Alternatives. SELECT … FOR UPDATE then update: correct, but two round trips and a longer lock. Optimistic version column: correct, but most requests fail and retry under contention. One row per seat with a unique constraint: right for numbered seats, overkill for counts. Distributed lock (Redis): extra infrastructure when the database is already the source of truth. Limitation: one very hot slot is bounded by row-lock throughput.

Challenge 2: Idempotency (BR4)

Design. A shared middleware handles endpoints marked unsafe. It (1) fingerprints the request: SHA-256 of method, path and canonical JSON, so key order and whitespace do not matter. (2) It runs INSERT … ON CONFLICT DO NOTHING on (key, scope) in the service's own idempotency_keys table, so the unique key is the lock. Two identical requests at the same moment cannot both win. (3) The winner runs, and its status and body are stored. A repeat is replayed with Idempotency-Replayed: true. A different fingerprint gets 422. A request still in progress gets 409 REQUEST_IN_PROGRESS with Retry-After. A 5xx releases the key, so the client may retry. Booking calls Payment with derived keys pay-{bookingId} and refund-{bookingId}, so even Booking's own retries cannot double-charge. Payment finishes an in-flight charge even if the caller disconnects: we found that otherwise an empty body was stored and replayed.

Evidence (evidence/challenge-2-idempotency/, 20/20 checks)Result

Alternatives. In-memory cache: lost on restart, not shared across replicas. Redis: extra infrastructure, and it separates the key from the data it protects. A unique business constraint alone (e.g. one payment per booking) does not return the original response. Limitation: keys are scoped per path, not per client (no authentication). They are deleted after 24 h.

Challenge 3B: Time-bound holds (BR2), with BR3 compensation

Design. Each hold has expires_at = now + TTL. A background worker (every 5 s, also exposed as POST /admin/holds/expire-now) claims due holds with SELECT … WHERE status = 'HELD' AND expires_at <= now FOR UPDATE SKIP LOCKED. It applies the domain rule Hold.Expire() and returns capacity in the same transaction. Safe to run twice: only HELD rows qualify, so a second run finds nothing. Never releases a paid slot: confirm takes the row lock and requires expires_at > now, so confirm and expiry race on one row and exactly one wins. Multi-replica safe: SKIP LOCKED lets several sweepers split the work. Booking treats Scheduling as the source of truth: its reconciler asks for the hold before marking a booking EXPIRED, so two clocks can never disagree. If payment lands after expiry, the confirm fails and Booking refunds automatically.

Evidence (evidence/challenge-3b-holds/, 18/18 checks, TTL 30 s)Result
Unpaid holdEXPIRED by the worker; capacity 1 → 0; booking EXPIRED; BOOKING_EXPIRED notification
Sweep run twiceSecond run expires 0; capacity not released twice

Alternatives. A per-hold timer in memory: lost on restart, not shared. A broker's delayed messages: a new dependency, and still needs an idempotent consumer. Database TTL/cron: same SQL, less visible. Limitations: expiry granularity is the sweep interval (a hold can live up to TTL + 5 s; confirmation enforces the exact TTL). A refund that fails after a late payment is only logged.

Beyond the required challenges. Booking's calls to Scheduling and Payment use timeouts (2 s per attempt), retries with exponential backoff and jitter, and a circuit breaker (Polly). The e2e script shows the circuit opening during a gateway outage (DOWNSTREAM_CIRCUIT_OPEN) and closing after 15 s; the retry with the same key then charges exactly once. This is the Challenge 3A bonus behaviour, kept safe by Challenge 2.

8. Design decisions and trade-offs

#DecisionOptionsChoice and rationale
D1Number of services5 (separate Catalog) vs 44. Catalog and availability change together; one fewer hop; can be split later if catalog reads dominate.
D2CoordinationOrchestration vs choreographyOrchestration in Booking. The flow and its compensation (release, refund) are explicit, in one place and unit-testable. Choreography would need a broker and scatter the logic.
D3CommunicationSync REST vs async messagingSync REST where the customer waits (hold, pay, confirm); outbox + async dispatch for notifications so an SMS outage never blocks or undoes a booking. The outbox maps directly to a broker later.
D4ConcurrencyPessimistic lock, optimistic version, atomic conditional updateAtomic conditional update for the contended slot (one statement, shortest lock, no retry storm); row locks for low-contention hold/payment updates.
D5Idempotency storageMemory, Redis, own DB tableOwn DB table per service. Survives restarts, works across replicas, keeps database-per-service, no new infrastructure.
D6Checkout shapeOne-shot vs hold-then-payHold-then-pay. Mirrors real payment pages, gives holds a real lifetime, and makes the late-payment case visible and handled.
D7Serialising work on one bookingDB lock across HTTP calls, version only, leaseShort lease (locked_until) + version. No DB lock is held while calling other services; a crashed operation's lease simply expires.
D8Multi-tenancyDB per tenant vs tenant_id columntenant_id on every row. Cheapest to run; large tenants can move to dedicated databases later.

9. Limitations and future work

  • No authentication: tenantId and customerId are trusted from the request. Next step: OIDC with tenant claims at an API gateway.
  • Synchronous orchestration: if Scheduling or Payment is down, new bookings fail fast (503) rather than queue. Timeouts, retries and the circuit breaker bound the impact.
  • A refund that fails after a late payment is only logged (manual follow-up); next: refunds through the outbox. Retrying a cancellation across the 24 h boundary computes a different refund and gets 422.
  • Slots are created explicitly; recurring schedules, waitlists, memberships and discounts are planned as new services, not rewrites.
  • One PostgreSQL server hosts the four databases locally (separate logins). Separate instances, a broker (RabbitMQ via the outbox) and OpenTelemetry tracing are the next scaling steps.
